# Database Contracts

## Authority
- PostgreSQL is the authoritative system of record.
- Neo4j is a derived projection; it must be rebuildable from PostgreSQL.

## Layering
The system stores data in layers to prevent data loss and to separate concerns:

1) Raw Layer (lossless)
- Preserves GEDCOM leveling structure and all tags/values exactly as read.
- Never discards unknown or malformed content.
- Purpose: audit, replay, re-standardize, and debugging.

2) Canonical Layer (standardized + normalized)
- Stores standardized entities and relationships in queryable form.
- Purpose: correctness, integrity, analytics, and projection.

3) Fact Layer (coverage for all tags)
- Any tag not mapped to canonical columns MUST still be represented as a fact.
- Purpose: guarantee “every tag exists somewhere” even while the canonical model evolves.

4) Enrichment Layer (additive)
- Stores derived interpretations, variants, and improvements.
- Enrichment never overwrites canonical standardized fields.
- Enrichment outputs are versioned and confidence-scored.

## Identity
- Internal stable IDs are generated by the system.
- GEDCOM xrefs and external IDs are stored as provenance, not primary identity.

## Provenance
Every stored fact must be traceable to:
- ingestion_run (run_id)
- file (file_id, sha256)
- GEDCOM xref (if applicable)
- raw node pointer(s) when available

## Idempotency
- Re-ingesting the same file under the same configuration must be deterministic.
- The system must define whether identical re-ingestion:
  - creates a new run snapshot, or
  - merges/upserts into a “current” canonical state.
This policy must be explicit and documented (no silent drift).

## Required Auditability
- Parsing warnings/errors are recorded with severity and stage.
- Canonical rows store source references (xref, file_id/run_id, etc.).
- Enrichment rows store input fingerprints and algorithm versions.
